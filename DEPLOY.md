# Деплой prof-equip.ru — инструкция для заказчика

Простыми словами: правки живут на test3, попадают на прод только через
`git` и скрипт `deploy.sh`. Никаких правок файлов на проде напрямую по SFTP —
их сотрёт при следующем обновлении.

## Как выкатить изменения

1. Изменения разрабатываются и проверяются на test3, коммитятся в ветку,
   пушатся в репозиторий.
2. Ветка сливается в `master` (через Pull Request на GitHub или локальным
   `git merge`).
3. На проде выполняется:

   ```bash
   /var/www/wordpress/local/deploy/deploy.sh
   ```

   Одна команда. Скрипт сам: проверит, что на проде нет посторонних правок,
   снимет бэкап, подтянет код из `master`, применит миграции БД, сбросит
   кэш, поправит права на файлы и прогонит проверку живых страниц.

## Как понять, что всё прошло успешно

В конце вывода `deploy.sh` — строка:

```
=== Деплой <хэш коммита> завершён успешно ===
```

Если чего-то не хватает — скрипт остановится на первой же ошибке с понятным
сообщением, ничего дальше делать не будет. Все действия дополнительно
пишутся в `/var/log/prof-equip-deploy.log`.

## Что делать, если что-то сломалось

Одна команда:

```bash
/var/www/wordpress/local/deploy/rollback.sh
```

Она покажет, к какому состоянию кода и базы откатит, и спросит
подтверждение (нужно ввести `да`). Без этого подтверждения ничего не
меняет. По умолчанию откатывает к последнему бэкапу деплоя; можно указать
конкретный:

```bash
local/deploy/rollback.sh deploy-2026-09-01-2130
```

(список доступных — `ls /backup/`).

## Чего нельзя делать никогда

- Править файлы на проде напрямую (SFTP, редактор в панели хостинга и т.п.)
  после того, как эта схема внедрена. Любая такая правка будет молча
  затёрта следующим `deploy.sh` (шаг `git merge --ff-only`), либо, если она
  попала в отслеживаемый git-ом файл, `deploy.sh` вообще откажется
  запускаться и потребует сначала разобраться, откуда правка.
- Заливать дамп базы с test3 на прод. На проде — реальные заказы. Изменения
  структуры базы переносятся только через `local/migrations/`.
- Запускать `deploy.sh` без бэкапа — скрипт делает это сам, отключать нельзя.
- Запускать `git reset --hard` / `git clean` / `git checkout .` на проде
  вручную, тем более без консультации.

## Проверить, что живой сайт в порядке, вручную

```bash
local/deploy/smoke.sh
```

Список проверяемых страниц — в `local/deploy/smoke-urls.txt`, можно
дополнять своими важными разделами (по одному пути на строку).
